# 额度分配

> 七个角色共用一个额度池，所以分配的本质只有一句话：把贵的算力留给"换掉它就做不对"的地方。本文只讲档位策略，不写具体模型 ID——ID 迭代太快，档位与模型的对应关系见 README 的「模型档位」一节。

## 一个订阅怎么分给七个角色

先说前提：订阅是一个池子，不是七个钱包。没有"规划用这份、执行用那份"这种事，所有角色花的是同一份额度。

于是问题变成：哪些角色换成弱一点的模型，工作质量几乎不掉；哪些角色一换就出问题。判断只用三个维度：

1. **调用频次**。次数多的角色，单次省一点就是大头；次数少的角色，省它没有意义。
2. **失败代价**。写错代码、判错方向，代价是返工；标题起得难看，代价是难看。
3. **是否需要异构**。纠错位置的价值来自"换个脑子看"，同源模型互相复核等于自己审自己。

按这三个维度切，七个角色会自然落成四层：主力、异构评审、便宜检索、工具档。

再换个角度看，七个角色在流程里出场的方式也不一样，这决定了档位能不能"平均分"：

- **每次都出场**：`build` 是会话入口，`title` / `summary` 在每次会话里自动跑。前者决定整场怎么走，后者只是登记。
- **干活的中间段**：`plan` 出规格、`general` 写代码、`explore` 找东西，一轮任务里可能被拉起好几次，也可能一次都不拉。
- **关口才出场**：`advisor` 在要评审时出现，`final` 在要定稿或出现冲突时出现，`compaction` 在上下文快满时出现。
- **独立支线**：`writer` 不参与技术链路，写文档、写文案时才叫。

所以分配不是"七个角色平摊"，而是"按出场位置配"：出场越靠近判断、越靠近收尾，越不能省；出场越机械、越频繁，越该便宜。

## 档位表（角色 / 需要什么能力 / 为什么）

| 档位 | 挂哪些角色 | 需要什么能力 | 为什么放这一档 |
|---|---|---|---|
| 主力强模型 | `build` / `plan` / `general` | 长上下文、长链推理、能读写代码、能按规格拆解任务 | 三个角色决定"做什么、怎么拆、写成什么样"，错在前面，后面全错。这是全流程唯一值得用最强档的位置 |
| 异构评审 | `advisor` | 推理能力接近主力，且**与主力不是同一家** | 它的职责是换个角度找漏洞。同一个模型家族的错误分布重合，复核会一起漏 |
| 异构仲裁 | `final` | 推理强，且与主力、评审都不同源 | 只在定稿、改过两轮、意见冲突时出场。低频，但一次判断决定要不要收工 |
| 便宜大额度 | `explore` | 只读检索、能吞下大量文件、响应快 | 任务是"找到并摘出来"，不需要深度推理；调用量大，用便宜档才可持续 |
| 中文强 | `writer` | 中文表达、结构感、排版意识 | 输出是给人看的文字，不写代码、不做技术判断；不常调用，但中文差一眼能看出来 |
| 最便宜快速档 | `title` / `summary` | 只要快，输出几十个字 | 每次会话都自动跑，是最频繁的调用；质量差一点没人察觉，慢一点每次都要等 |
| 默认档（非最低档） | `compaction` | 读懂长对话、保留要点不丢信息 | 偶发操作，速度不敏感，质量直接决定压缩后还剩下多少上下文 |

表里没有金额，也没有"用掉多少"。档位是结构问题，跟具体价格无关：换个套餐，结构不变。

读表时容易忽略的三点：

- **同一档里可以有多个角色**。`build` / `plan` / `general` 共用一个档，因为它们读写的上下文高度重叠，换模型反而会让规格和执行对不上。
- **档位不等于强弱排序**。`writer` 那一档未必比主力弱，只是它点的是另一棵技能树：中文表达和代码推理无法用同一个档位衡量。
- **隐藏代理也算角色**。`title` / `summary` / `compaction` 不在会话选择器里出现，但一样消耗额度，一样需要单独配档。

## 三条原则

**第一，高频的用便宜的。** `title` / `summary` 和 `explore` 是调用次数最多的三个角色。它们的特点是错了不要紧——标题可以重生成，检索可以再搜一次。高频乘低价值，就该配最便宜的档；给它们配最强模型，等于每次会话开头先烧一笔。

**第二，纠错的位置用异构的。** `advisor` 和 `final` 的全部意义是"换个脑子看"。如果它们和主力同源，看到的是同一批盲区，复核只是把同样的结论又说一遍，形式上过了，实际没验。省钱可以省在检索上，不能省在异构上——省掉异构，等于把这套多角色结构退化成单模型自问自答。

**第三，偶发但关键的用好的。** `final` 可能几天才叫一次，`compaction` 半天才触发一次。正因为低频，它们的额度开销可以忽略，没有理由降级。反过来说，最不该克扣的就是这种"一年用不了几次、用一次定生死"的位置。

三条原则打架时的排序：**异构 > 偶发关键 > 高频便宜**。理由是它们换来的东西不同——异构买到的是"能查出错误"，偶发关键买到的是"收尾不出事"，高频便宜买到的只是"省一点"。前面两样丢了没法用返工补回来，最后一样丢了只是账单难看。

反例最能说明问题：为了省钱把 `advisor` 换成主力的同源模型，表面上三个原则都满足了（便宜、配了、有评审），实际是把整套结构里唯一"能发现主力错了"的位置取消了。这类改动不会立刻报错，只会在某次该拦没拦住的时候暴露。

## 换套餐怎么改

档位是结构，模型是填充。换套餐只换填充，不动结构。按手上的牌分两种情况：

**情况一：只有一家模型可选。**

| 角色 | 怎么配 | 损失什么 |
|---|---|---|
| 主力 | 该家最强档 | 无 |
| `explore` / `title` / `summary` | 该家最便宜的快速档 | 无，本来就该用便宜档 |
| `advisor` / `final` | 该家次强档，或最强档的另一代版本 | 交叉验证失效：复核与主力共享盲区，纠错只是复述 |
| `writer` | 该家中文表现最好的一档 | 可能中文不如专门的中文模型，但不影响技术判断 |

结论：**能跑，但纠错能力弱。** 这不代表配置坏了，只代表"验证者比被验证者更可信"这条前提被削弱了——验收时要更依赖可执行的检查（脚本、测试），而不是依赖评审的直觉。

**情况二：有两家模型可选。**

把两家分给"写"和"审"：一家做主力（`build` / `plan` / `general`），另一家做 `advisor`；`final` 用其中较强的一家，或者第三家。`explore`、`title`、`summary` 随便挑便宜的那边。

结论：**结构完整。** 只有一个注意点——不要为了"看起来异构"把主力拆到两家：同一个流程里 build 和 general 用不同模型，上下文传递容易出现理解偏差，得不偿失。

**情况三：额度紧张，必须往下砍。**

砍的顺序是固定的，从最不值钱的地方开始：

1. 先把 `explore`、`title`、`summary` 压到最便宜的可用档——这三处压到底也几乎不掉质量。
2. 再把 `writer` 降到中间档——写作任务失败的成本是多改两遍，可以接受。
3. 然后动 `compaction`——它虽然偶发，但压缩质量差会影响后续整段会话，放到第三步。
4. 最后才考虑 `advisor` / `final`——到这一步说明额度已经不够支撑这套结构，正确的做法是减少委派轮次，而不是把异构拆掉。

顺序反了就会出怪现象：评审便宜了，返工变多，额度反而更快见底。

## 常见分错的方式

**所有角色都配最强模型。** 最直觉也最贵的一种。问题不只是慢和贵：七个角色全用同一个模型，等于取消了交叉验证，多角色只剩多轮往返的成本，没有了复核的收益。

**所有角色配成同一家的不同版本。** 看起来分了档，实际是同一套权重训出来的几个尺寸。便宜档和强档的盲区高度重合，`advisor` 说"没问题"时，你无法判断是真的没问题，还是它和主力想到了一块。

**给 `title` / `summary` 配大模型。** 这两个角色每次会话都跑，是纯粹的机械活。配大模型只有两个结果：每次开头多等几秒，额度被最不值得的地方吃掉。同理，给 `explore` 配最强档也是浪费——检索不需要深度推理。

**为了省额度把 `final` 降级。** 看起来最划算，实际最亏。它调用频率最低，省下来的份额很小；但它出场时通常正是"要不要收工"的关口，判断错了，前面所有轮次都白跑。

**忘了 `compaction` 也算一份。** 它不出现在会话选择器里，容易被当成不存在。长会话触发压缩时，压缩质量差会直接丢掉关键上下文，后面所有角色都在残缺信息上工作。

一句话收尾：分配的难点不在"哪个模型更强"，而在"哪个位置换掉它仍然做得对"。答错这个问题，省下的额度都会以返工的形式还回去。
