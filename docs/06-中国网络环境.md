# 中国网络环境

> 这一章只讲判断，不给数字。原因见最后一节。

## 走聚合和走直连的区别

**直连**：每个模型商一套 key、一份账单、一个后台。网络路径短，少一跳。

**聚合**（例如把多家模型收进同一个订阅）：一份 key 覆盖多家模型，账单和额度合成一本账。代价是请求要多经一跳。

这是取舍，不是优劣：

| | 聚合 | 直连 |
|---|---|---|
| 账单与凭据 | 一套 | 每家一套 |
| 网络路径 | 多一跳 | 少一跳 |
| 某家服务出问题 | 可能一起受影响 | 只影响那一家 |
| 换模型的成本 | 改一个模型 ID | 换 key、换基址 |

真正决定体验的，往往不是"平均快多少"，而是**某一跳在你所在网络下是否稳**。同一个方案，换个城市可能就是另一种结果。

## 常见的三个卡点

下面三条是现象和可能原因，不是诊断结论。**都不给时间数字**——同一条现象换个运营商就是另一种成因。

### 1. 首次调用慢，后续正常

可能是热启动，也可能是路由在挑节点。第二次、第三次如果明显恢复正常，通常不算故障，等它稳住即可；连续多次都一样慢，才值得往下查。

### 2. 某个 MCP 拉取或装依赖卡住

现象：模型能正常对话，但某个 MCP 服务起不来，或 `npx` 拉包一直停在原地。

大概率是**包源**问题，不是模型问题。换一个镜像源、把依赖预装到本地、或改成从已装好的本地路径启动，通常比反复重启 opencode 有效。

### 3. 长会话中途变慢

会话越聊越慢，通常和网络无关：上下文变长，每次请求要处理的内容更多，响应自然变慢。

先看上下文体积，再怀疑线路。压缩会话或开个新会话接着聊，常常比换方案有效。

## 代理怎么配（原则，不是教程）

具体软件和参数会过期，这里只给四条不会过期的原则：

1. **配在系统层或环境变量层，不要在单个工具里硬编码。** 标准的代理环境变量（如 `HTTPS_PROXY`）配一次，所有工具都吃得到；写死在某个配置文件里，换个工具就要再配一遍，还容易漏。
2. **配完立刻用一条最小请求验证。** 一次最简单的对话即可，通了再往下配角色、配 MCP。先堆一堆配置再验证，出问题时不知道是哪一层坏的。
3. **凭据不进仓库。** 代理地址和账号密码放进环境变量或系统设置，不写进 `opencode.json`、不写进 `AGENTS.md`、不提交。仓库里的配置是给别人抄的，抄走你的代理等于抄走你的出口。
4. **只用一种手段。** 系统代理和工具内代理同时开，容易互相覆盖甚至形成环路，出问题时极难定位。

## 什么时候该换方案

两个信号，够用：

- **延迟影响到日常使用**：不是"感觉有点慢"，而是具体到"每次问答都要等，等到不想用"。到这个程度，换方案比忍着划算。
- **某个必需功能在该方案下不可用**：比如要用的 MCP 在聚合下拿不到，或某个模型在你这里根本连不上。功能缺失没有折中，只能换。

不构成换方案理由的：偶尔一次的慢、别人贴的测速图、某一天某一小时的抖动。这些多半是时段问题，过一阵再看。

## 本文档没有实测数据

**这一章不含任何实测延迟数字，是刻意的，不是漏写。**

原因：延迟的变量太多——所在城市、运营商、国际出口拥塞情况、访问时段、当天的路由——任何写死的数字，对另一个人基本都是错的。写一句"平均 X 秒"，只会让读者拿一个跟自己无关的基准去对比，然后误判自己的环境出了问题。

替代做法：**自己测一次最小请求。**

- 发一条最简单的对话请求，从发出到看到第一个字符，自己读一下耗时。
- 同一请求连做三次，取你自己稳定的那个值，这就是你的基线。
- 之后感觉"变慢"时，和这个基线比，而不是和任何文档比。

同样的道理，本章也不写成功率、可用率这类指标。你的环境只能由你自己的观测来定义。
