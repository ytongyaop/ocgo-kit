# 踩过的坑

> 这一章只记搭建这套配置体系本身踩过的坑，不记业务开发的坑。
> 每个坑固定三段：现象、原因、修法。都真实发生过，表述已脱敏。
> 多数坑能用 `scripts/doctor.mjs` 提前拦住；装好之后的症状对照见 `docs/07-自查手册.md`。

## 1. 把敏感词字面量写进仓库，永远过不了自己的检查

**现象**：文档为了演示"怎么检查隐私泄露"，把真实姓名当成 grep 关键字写进了正文。检查方法自己成了泄露源——用敏感词扫描扫自己，必命中自己。

**原因**：演示素材和检查对象混在了一起：用来扫描的词表，进了被扫描的范围。

**修法**：词表放仓库外，仓库里只留检查方法。

- `docs/PRD.md` 的成功标准第 1 条就是这么定的：用仓库外的私有词表执行 `grep -riF -f <敏感词表>.txt .`，返回空才算过。
- 文档需要举例时，用 `SENSITIVE_WORDS.txt` 这类占位文件名，词本身一个字都不进正文。

## 2. 文件内容脱敏了，git 历史没脱敏

**现象**：所有 `.md` 都改干净了，公开前一看 `git log`，author 和邮箱还是真实信息。

**原因**：commit 元数据不随文件内容改变——改文件只产生新提交，旧提交的作者字段原样留着。

**修法**：两条路。一是公开前统一用 `git rebase --root` 配合 `--reset-author` 重写全部历史；二是一开始就在仓库本地配中性身份，一劳永逸：

```bash
# 在仓库目录里执行；不加 --global，不影响其他仓库
git config user.name "your-handle"
git config user.email "you@example.com"
```

重写历史是补救不是常规操作：改完必须强推，别人克隆过就对不上了。

## 3. 记忆文件路径和配置不一致，记忆静默失效

**现象**：memory MCP 的 `MEMORY_FILE_PATH` 指 A 路径，`AGENTS.md` 里写的是 B 路径。看起来都装好了，但记忆不生效，也不报错。

**原因**：两处路径各有消费方——一处给 MCP 进程读写用，一处给主管按规则找文件用。两边指的不是同一个文件时，配置"在"，链路没接上，且谁都不报错。

**修法**：只认一处事实源——`opencode.json` 里的 `MEMORY_FILE_PATH`。`AGENTS.md` 不再写第二份具体路径，只说"`MEMORY_FILE_PATH` 指定的那个文件"，模板现在就是这么写的。

验证靠体检：`node scripts/doctor.mjs` 的 `memory MEMORY_FILE_PATH` 一项，会打印解析后的绝对路径和文件是否存在。

## 4. 把私有工具的绝对路径写进示例配置

**现象**：模板里的 MCP 启动命令写了一个只有作者机器上才有的可执行文件的绝对路径，别人复制配置过去，启动就报错。

**原因**：示例配置直接从自己跑通的配置里抄，没逐项过一遍"读者机器上有没有它"。

**修法**：示例只放一行命令就能装上的依赖（如 `npx -y <包名>` 形式）；装不上的工具两个处理——整段删掉那个 MCP 条目，或标为可选并写清安装方式。`config/AGENTS.md` 里那句提醒因此保留：不用的一律删掉，配了没装，启动会报错。

## 5. 把 `<>` 尖括号占位符写进路径类配置

**现象**：权限白名单里写 `"<你的工作目录>/**": "allow"`，看起来清楚，但它不是合法路径，解析会出问题，权限项等于没配。

**原因**：尖括号是给人看的"替换我"标记，而 JSON 配置值会被程序直接消费——程序不认人的约定，JSON 连注释都不支持。

**修法**：路径类占位符一律写成能直接跑的形式，说明放配套文档里。

错的写法：

```
"<你的工作目录>/**": "allow"
```

对的写法（`YOUR_USERNAME` 自己替换）：

```
"C:/Users/YOUR_USERNAME/workspace/**": "allow"
```

`doctor.mjs` 的 `permission 路径键合法性` 一项专抓这个：含尖括号的键直接 FAIL，并指出是哪个键。

## 6. 同一个角色定义在两个地方

**现象**：一个角色的提示词既写在 `opencode.json` 的 `agents` 段，又写了 `agent/xxx.md`。改的时候只改了一边，行为对不上预期，也说不清哪份在生效。

**原因**：两份定义并存时哪份生效，取决于 opencode 版本的合并规则——`docs/07-自查手册.md` 里也标注了未验证。把配置的正确性押在没验证过的合并行为上，不可靠。

**修法**：一个角色只定义一处。本仓库的切法：build / plan / general / explore 内联在 `opencode.json` 的 `agents` 段；advisor / final / writer 各占 `config/agents/` 一个文件。发现两边都有，删一边、留一边。

## 7. 目录单复数搞错，角色神秘消失

**现象**：角色文件装进了 `agents/`（复数），而 opencode 读的目录是 `agent/`（单数）。会话选择器里只剩 build，没有任何报错。

**原因**：仓库里的源目录叫 `config/agents/`，安装目标目录叫 `agent/`，两个名字本来就差一个字母；放错之后 opencode 也不提示。

**修法**：安装脚本和文档统一把目标目录写成单数 `agent/`——`docs/01-安装.md` 的映射表和 `install.mjs` 现在都这么定。

装完用体检核对：`node scripts/doctor.mjs` 的 `agents advisor/final/writer` 一项显示 3/3，才算真装上了。

## 8. 记忆越攒越大，反而拖慢每次会话

**现象**：什么都往记忆里写，排障过程、复盘、临时状态全进热层。每次会话开场必读的几个实体被塞满，真正要紧的规则被挤出了上下文。

**原因**：记忆的成本不是钱，是信噪比：热层每次会话都全额注入，无关内容每多一行，规则的权重就被稀释一分。

**修法**：三条，都落在 `config/AGENTS.md`「记忆维护」一节：

- **分三档**：热层只留每次必读的少数实体；其余细节按需检索；过程性内容一律进冷层存档，记忆里只留结论和指针。
- **定预算**：热层合计约 8,000 字符，温层单实体不超过 4,000 字符，一条观察不超过 160 字，超长当场拆。
- **机器查**：`scripts/memory-lint.mjs` 把预算和红线变成可执行规则；lint FAIL 时不得宣称维护完成。

## 9. 文档承诺了还没写的东西

**现象**：README 的目录链到九个章节，实际只写完两个，读者点进去不是 404 就是空文件。

**原因**：目录按计划先写，文件按进度后补，两者不同步时没有任何机制提醒。

**修法**：两个动作。

- 没写完的章节不给裸链接，链接后面标"（待补）"；章节写完后立刻回查所有引用它的地方，把标记清掉——漏掉一次，读者点进去就是空的。
- 发布前跑一遍死链检查：`doctor.mjs` 对总纲有 `AGENTS.md 死链` 一项，会列出解析不了的引用和行号；README 里的外链要自己点一遍，或交给任意链接检查工具。
