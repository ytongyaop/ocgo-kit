# 推荐技能

> 这一章给出值得装的技能清单和明确不推荐的类别，都附理由。
> 按 `docs/PRD.md` 的边界：不打包第三方技能；技能名以各上游仓库为准，本章不写下载与安装命令。

## 技能是什么

opencode 的 skill 是按需加载的说明文档：平时躺在磁盘上不占地方，任务命中或被点名调用时，才加载进上下文、才开始占上下文。

它不是插件：不改变 opencode 的程序行为，不增删工具。有的技能附带脚本和模板，但主体仍是文本——出问题可以直接读、直接改，和本仓库"透明"的定位一致。

按需加载之所以重要，是因为上下文是稀缺资源：常驻 prompt 每多一行无关内容，规则的权重就被稀释一分——和记忆分档是同一个道理（见 `docs/04-记忆模式.md`）。技能把"做法"从常驻规则里挪出来，用的时候才付费。

所以选技能只有两个成本：用的时候值不值那份上下文、它的做法和现有规则冲不冲突。不存在"装坏了 opencode"的风险。

## 值得先装的几个

| 技能 | 用来干什么 | 什么时候用 |
|---|---|---|
| `grilling` | 反复追问需求，逼出没说清的前提 | 需求含糊、要出规格之前 |
| `codebase-design` | 深模块设计词汇：接口、边界、可测试性 | 设计模块结构时 |
| `find-skills` | 让 agent 自己发现还能装什么技能 | 不确定有没有现成方案时 |
| `skill-creator` | 把重复出现的做法固化成新技能 | 同一类任务做过三次以上 |
| `docx` / `pptx` / `xlsx` / `pdf` | 读写办公文档格式 | 要交付文档、表格、演示稿时 |
| `frontend-design` | 做界面时避免通用 AI 风格 | 需要 UI 时 |

选这几组的标准：各自对应工作流里的一个环节，不是看到什么装什么。

`grilling` 对应规格环节。plan 子代理的提示词里就写着：需要逼问需求时，建议主管加载 grilling 技能，不要自行扮演访谈——追问这件事交给专门写好的追问文档，比让规划角色即兴发挥稳定。

`codebase-design` 对应架构与重构判断，这正是 advisor 要评审的那类问题。它给的是一套共享词汇（接口、边界、可测试性），规划和评审说同一种话，来回翻译的损耗就小。

`find-skills` 和 `skill-creator` 是一对：前者解决"不知道有没有现成的"，后者解决"同一类活干过三次，该固化下来"。固化出的新技能放进自己的技能目录，和本章清单遵循同一套按需加载规则。

办公四件套（`docx` / `pptx` / `xlsx` / `pdf`）对应 writer 类交付：文案由 writer 写，落成 Word、表格、PDF 时的格式处理交给技能，不靠手改排版。

`frontend-design` 的适用面窄，但命中时难以替代：它的目标就是避开"一看就是 AI 画的"那种通用界面风格。

怎么装：把技能目录加进 `opencode.json` 的 `skills` 数组（字符串数组，相对路径、`~/` 路径、绝对路径、http(s) URL 都支持；但传给子进程的字段如 `MEMORY_FILE_PATH` 不保证展开 `~`，为稳妥建议统一写绝对路径），技能文件放进去后重启 opencode。旧版本支持对象形式 `{"paths": [...]}`，已被标为弃用，用数组即可。示例配置 `config/opencode.json.example` 的 `skills` 段就是一条这样的路径。各技能的来源不同、下载方式会变，这里不写具体命令，以各自上游仓库为准。

清单没有先后次序，六组都按需装：不做 UI 就不用装 `frontend-design`，不交付办公文档就不用装四件套。

## 它们从哪来

这些技能来自三个不同的上游仓库，不是同一套：

| 技能 | 上游仓库 | 目录 |
|---|---|---|
| `grilling` / `codebase-design` | [mattpocock/skills](https://github.com/mattpocock/skills) | `skills/productivity/grilling/`、`skills/engineering/codebase-design/` |
| `find-skills` | [vercel-labs/skills](https://github.com/vercel-labs/skills) | `skills/find-skills/` |
| `skill-creator` / `frontend-design` / `docx` / `pdf` / `pptx` / `xlsx` | [anthropics/skills](https://github.com/anthropics/skills) | `skills/` 下同名子目录 |

两点提醒：

- **许可不一样**。`anthropics/skills` 里的文档四件套（`docx` / `pdf` / `pptx` / `xlsx`）是 source-available，不是开源许可；其余示例技能多为 Apache 2.0。拿去商用或再分发之前，先读一眼上游的 LICENSE。
- **本仓库不打包、不镜像**这些技能，只给链接。上游更新或改名，以那边为准。

## 明确不推荐的

不推荐不等于技能本身不好，而是和本仓库的定位冲突、或不适合放进公共推荐。三类：

**1. 云厂商全家桶类技能**

- 什么样：一次几十个，覆盖某个特定平台的登录、部署、计费、监控等全套操作。
- 为什么不推荐：和"一个订阅跑通"的定位冲突——本仓库的模型调用全部走一个订阅，不需要再按厂商配一套工具链；而且几十个条目会让读者困惑该用哪套，多数人根本用不上其中大部分。

**2. 绑定某一家模型的技能**

- 什么样：工作流只服务某一家 API，换个模型就跑不通。
- 为什么不推荐：本仓库的原则是"角色可换模型"——档位绑定的是位置，不是厂商，模型迭代时换个 ID 就行。绑死一家的技能会把替换成本从"改一行配置"抬高到"改一套工作流"。

**3. 私人用途的领域技能**

- 什么样：只针对某个具体课题、某个行业。
- 为什么不推荐：不具通用性，还常内嵌作者自己的私有路径和资料，不适合放进公共推荐。有这类需求，用 `skill-creator` 自己写一个，正好落在自己的技能目录里。

## 技能和门禁的关系

技能是辅助，不能绕过门禁。四条硬规则（原文在 `config/AGENTS.md`）对带技能的活同样成立：没有可测验收标准不进计划、只动计划内文件、每个可验证增量一停、报数字必须贴命令输出。技能再专业，也不能代替这四个动作。

`config/AGENTS.md`「技能与知识库」一节还写了两条纪律：

- **调用前先说明"用哪个、为什么"**。防止模型为了用技能而用技能——每次加载都花上下文，白花就是亏。
- **产出只落进已有文件，不新建平行文档体系**。技能常自带一套文档约定和目录结构，放任它自建体系，仓库里就会出现两套事实，违反单一事实源。

反过来，门禁也不干预技能内部怎么干活：用哪个步骤、加载哪份模板，是技能自己的事。约束只有一条——产出要回到已有文件和已有验收流程里来。

一句话收束：技能决定"怎么做得专业"，门禁决定"做没做完算不算数"；前者服务后者，不替代后者。
