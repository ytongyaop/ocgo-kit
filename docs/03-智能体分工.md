# 智能体分工

> 这一章只讲角色的职责与边界：七个角色各自吃什么、吐什么、绝对不做什么。
> 拆角色的设计理由见 `docs/00-为什么这样搭.md`；什么时候叫谁、触发器全表见 `config/workflows/委派.md`。
> 角色定义的唯一事实源在 `config/` 下：build / plan / general / explore 内联在 `opencode.json` 的 `agents` 段，advisor / final / writer 各占 `config/agents/` 一个文件。本章是导读，不是第二份定义。

## 为什么要拆角色

一个 agent 既写又审，盲区是重合的：写的时候没想到的地方，审的时候同样想不到，错误正好落在同一处，查多少遍都是白查。

拆角色是为了让"写"和"判"用不同的上下文。写的人脑子里装着目标、代码和改法；判的人脑子里只装验收标准和 diff，不装"这段代码写得多辛苦"的心理包袱。两份上下文不重合，盲区才有机会不重合。

再进一步，评审和仲裁特意用与主力不同家的模型：主力之外换一家做评审，仲裁再与评审异构——不同模型犯的错不一样，异构才有交叉验证（档位对应关系见 README「模型档位」一节）。

代价是多几轮往返。这笔钱只在高赌注场合才值得花，所以委派顺序恒为从便宜到贵，判据是赌注而不是难度。`config/workflows/委派.md` 里这句话是原文：错误与难度无关，与赌注有关。

## 七个角色逐个说

**build（主管）**——编排者，不是执行者。

- 职责：澄清需求、拆任务、验收结果、安排谁干什么。
- 输入：用户的原始诉求；各子代理的回传。
- 输出：委派单（五要素齐全，见下文）、验收结论。
- 绝不：亲自改文件——谁改的谁就不该判；采信子代理自报的"已完成"，验收命令必须自己跑。唯一例外是会话内用完即弃、不落进项目的临时脚本。

**plan（规划）**——只读，只出方案，不出代码。

- 职责：把模糊的目标变成规格与计划。
- 输入：主管给的目标与约束；现状代码，用 read / grep 核对，不凭印象。
- 输出：方案文件，固定四段——目标（一句话，可验证）、范围（做什么、明确不做什么）、验收标准（每条能用一条命令或一次观察判定）、计划（步骤 + 涉及文件 + 每步验证方式）；外加未决问题清单。
- 绝不：写实现代码；信息不足时靠猜——列「未决问题」停下，由主管转达；写不出验收标准就删步骤——同样列未决问题等确认。

**general（执行）**——唯一能改代码的子代理。

- 职责：在委派范围内实现、调试、测试、连续工具操作。
- 输入：已确认的规格 / 计划与委派单。
- 输出：改动、验证命令与实际输出、改动文件与关键行号、未决问题。
- 绝不：自行扩范围（要扩先停下汇报）；自行 commit（改完报告，等主管确认）；用"应该没问题"代替跑 lint / typecheck / 测试。

**explore（检索）**——只读侦察兵。

- 职责：找文件、找定义、查官方文档与 GitHub 原始文件。
- 输入：一个具体问题。
- 输出：绝对路径 + 行号 + 不超过 3 行的关键片段；每个问题最多 10 条命中，超出按相关度截断并说明。
- 绝不：贴整文件；改任何文件；执行有副作用的命令；找不到时拿相似内容冒充——找不到就明说找不到。

**advisor（评审）**——只判断，不动手。

- 职责：三种模式——计划评审（出计划后、开工前）、过程复核（改完代码或交付后）、疑难咨询（多方案时给 2–3 个方案加代价与适用条件，明确推荐一个，并说明何时改选另一个）。
- 输入：方案文件、diff、疑难描述。
- 输出：先结论后理由；理由必须可执行——文件:行号或具体改法；不确定就写"不确定"，不编依据。
- 绝不：改文件、写代码、接管任务；能跑的只有只读验证命令（git diff、读文件）。

**final（仲裁）**——低频，不常驻。

- 职责：只在三种时候出场——要定稿了、已改过两轮以上、advisor 与 general 结论冲突；其余主管自己拍板。
- 输入：主管拉齐的双方结论与依据。
- 输出：裁决（定稿 / 再改一轮并写明改什么 / 采纳 A / 采纳 B）+ 依据（文件:行号或命令输出）+ 风险。
- 绝不：接管实现；做一线 review（那是 advisor 的活）；与 advisor 冲突时和稀泥——必须说清同意谁、为什么。

**writer（内容）**——只写，不跑。

- 职责：文档、PPT 文案、对外文字，成品直接拿去用。
- 输入：框架、材料、术语表，逐字沿用，不新增框架外章节。
- 输出：成品，外加三行交代——字数、数字出处、与框架不一致处。
- 绝不：做技术判断；改代码；跑命令——shell 权限在定义文件里直接 deny；资料里没有的数字一律写"[待补]"，不当事实编。

另有 title / summary / compaction 三个 opencode 隐藏维护代理，会话选择器里看不到它们，不参与上述分工（见 README「7 个角色」一节）。

## 边界是怎么划的

切分轴不是"轻活 / 重活"，而是两个问题：产出是否天然可机器校验、延迟是否可容忍。原话在 `config/workflows/委派.md` 第 2 节。

落到具体分工上：判据能写成代码的对账，一律给脚本——零 token、可重放，不叫任何 agent；机器校验不了的判断，按赌注从小到大上交——explore 做机械复核，advisor 管结构性改动与高赌注场合，final 只做仲裁。

延迟和价格决定档位：explore 用便宜的 Flash 档，可以高频派；final 用最贵的异构模型，低频派。急活留在主对话直接办，可容忍往返的才排进委派链。

还有一条隐含轴是可信度：验证者必须比被验证者更可信。所以验收绝不回流给干活的角色自己，主管也不碰文件——运动员不兼裁判。

边界不只写在提示词里，还锁在权限里：plan 的 edit 权限默认全 deny、只放行 `specs/` 方案目录；writer 的 shell 直接 deny。提示词可能被模型忽略，权限拒绝不会——双保险，边界才算划住。

每个角色只在一处定义：内联的四个在 `opencode.json` 的 `agents` 段，独立文件的三个在 `config/agents/`，两边不重复。两处都写会发生什么，见 `docs/08-踩过的坑.md` 第 6 坑。

## 委派时该给什么

五样缺一不可（`config/AGENTS.md`「委派五要素」原文）：

- **目标**：一句可验证的话。
- **范围**：做什么、不做什么。缺这项，子代理会自行发挥。
- **约束**：要守的规则、不能碰的红线。
- **可改文件**：白名单。缺这项等于授权越界。
- **验证方法**：跑哪条命令、什么输出算过。缺这项，"完成"只剩自报。

回传格式同样统一：结论 + 文件行号 + 验证输出 + 未决问题，不要全量日志——日志占掉主管的上下文，却帮不上验收。

还有一条结构约定：子代理不能再派子代理。plan 需要大范围检索时，在「未决问题」里写"请主管代调 explore"；层级保持扁平，调度权始终在主管手里。

顺序恒为从便宜到贵：脚本 → explore / general → advisor → final，前一档能解决就不升到下一档。

## 什么时候不该委派

三类事不委派：一句话能答的、纯闲聊、与当前工作无关的问答。主管直接答，不为一句话启动多个代理——这是 `config/AGENTS.md` 里的硬规则。

理由是算账：每次委派至少多一轮往返，拆分、写单、读结果都是开销。对小事来说，这笔开销高于自己动手的收益。README「给谁用」一节把话反过来说了：只是偶尔问 AI 一句话的人，多角色往返是负担，直接问模型才是对的做法。

另一类是可脚本化的机械活：清点、改名、查表、生成清单。判据能写成脚本就写脚本，零 token 且可重放，不叫任何 agent（触发器表见 `config/workflows/委派.md`）。
