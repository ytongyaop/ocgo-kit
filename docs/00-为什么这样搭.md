# 为什么这样搭

> 这一章是这套配置的设计说明：只讲判断和取舍，不写操作步骤——步骤在 `docs/01-安装.md`。
> 每一节都回答同一个问题：不这么做，会怎样。

## 为什么不是一个 agent 干所有事

最省事的做法，是一份长 prompt 让一个 agent 自己写、自己审、自己汇报。

问题在于既写又审等于自己判自己的卷：上下文里同时装着"要做什么"和"做得对不对"，越到后面越容易自己说服自己。

所以这套配置拆成三个角色：general 只管写，advisor 只管审，定稿再换一家 final 仲裁。

`config/workflows/委派.md` 把这个判断收成一句话：错误与难度无关，与赌注有关。

代价是多几轮往返。

## 为什么主管不碰文件

build 是主管：澄清需求、拆任务、验收结果、编排谁干什么。

它的提示词里有一条硬规则——不亲自改文件，改动一律委派。

理由一：谁改的，谁就不该判。主管自己动了手，就是运动员兼裁判，验收时盯着自己刚写的代码，会天然手松。

理由二是上下文：主管的脑子一旦塞满改动细节，"怎么拆、交给谁、怎么验证"就没地方放了。

代价是多一轮传话——比起自己改自己判造成的漏判，这轮传话是便宜的。

## 为什么验收不能自己做

写代码和查错，是两种能力。同一个模型既写又审，盲区是重合的：写的时候没想到的地方，审的时候同样想不到，错误正好落在同一处，查多少遍都是白查。

所以验收要换角色，最好换一家模型。

委派顺序也照此排：脚本 → general → advisor → final，从便宜到贵。能机械化的对账写成脚本，正式验收、事故后复核这类高赌注场合，才交给 advisor 以上。

一句话：验证者必须比被验证者更可信。

## 门禁解决什么问题

门禁四条定义在 `config/AGENTS.md`，此处不重复。它们不是流程洁癖，只做一件事：把"我觉得差不多了"，换成"这条命令过了"。

人和模型有个共同的毛病：最容易在自信的时候漏掉检查。

所以最狠的是第四条：报任何数字或"已完成"之前，必须能当场贴出产生它的最后一次命令输出，贴不出就标"未验证"。

这条不问能力，只在自信那一刻加一道绕不开的动作：要么贴证据，要么承认没验证。

## 单一事实源与记忆分档

同一件事写在两个地方，早晚会不一致，AI 无法判断哪份是新的，就会按错的那份走。

所以门禁只在 `config/AGENTS.md` 定义，流程只在 `config/workflows/` 写，每个角色只定义一处。

记忆分三档不是为了省钱，是信噪比：全量塞进上下文，无关信息会挤掉真正要紧的规则——所以热层要小，细节按需检索，过程性内容进存档。

分层预算与读写规则，见 `docs/04-记忆模式.md`（待补）。
