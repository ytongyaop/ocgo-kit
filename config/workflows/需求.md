# 需求

## 步骤
1. 问清四件事：谁用、解决什么痛点、硬约束（时间/钱/技术栈）、现在怎么凑合解决。一次只问一组，答完再问下一组。
2. 写 pitch 五要素，一屏内说完：
   - **Problem**：现状 + 痛点，一句
   - **Appetite**：准备花多少（小时/天）。固定时间不固定范围——超了就砍功能，不延期
   - **Solution**：v1 最小可用路径，具体到用户怎么操作
   - **Rabbit holes**：已知会陷进去的地方，点名
   - **No-gos**：明确不做什么，至少 3 条
3. 可行性三问：技术可行 / 经济可行 / 时间可行。任一"不行"→ 当场缩范围或劝退，不带着进 PRD。
4. 用户点头后落 `docs/PRD.md`：给谁用 / 解决什么 / v1 功能清单 / 明确不做什么 / 可测的成功标准。
5. 大改场景：回看 `docs/架构.md` 是否仍成立；需求变了先改 PRD 并写理由，不许代码里偷偷改。
6. 和用户约一个简短、唯一、稳定的代号，登记进 `记忆索引`；明细存 `work:记忆存档.md`。

## 产出要求
- pitch 五要素齐全，Appetite 有具体数字，No-gos ≥3 条。
- PRD 每条功能都能对上一句成功标准，标准写成"跑什么命令 → 看到什么"。
- PRD 只有 WHAT/WHY；出现函数名、库名、表结构就是写多了。

## 边界
- 只做"把模糊想法整形到可决策"；不做技术选型、不写代码、不排期。
- 硬规则见 `AGENTS.md#门禁`。
