# ocgo-kit

> 一个 OpenCode Go 订阅，养起 7 个分工明确的 AI 角色，不开第二个 API Key。
> 纯文本配置，不是插件：几个 `.md` 加一份 JSON 示例，每一行都可读、可删、可改。
> 和 oh-my-opencode 不是竞品，是两条路：那边给省心，这边给透明。

## 这是什么

一套 opencode 全局工作流配置：7 个角色、8 个流程、4 条门禁，全部写成纯文本。装上之后，opencode 会按"主管编排、规划出规格、执行改代码、评审做判断"的固定分工运转。

仓库里的东西：

- `config/AGENTS.md`——总纲。门禁四条、7 角色分工、模型档位、工具分工，都在这一个文件里。
- `config/opencode.json.example`——脱敏配置示例。build / plan / general / explore 四个角色的 system 提示词内联在这份 JSON 里，权限、MCP、memory 的设置也在这。
- `config/agents/`——advisor / final / writer 三个角色的独立定义文件，一个角色一个文件。
- `config/workflows/`——8 个流程说明书，一个流程一个 `.md`。
- `PROMPT.md`——安装作业单提示词，整段复制给你的 AI，它照单替你装。
- `scripts/`——三个脚本：`doctor.mjs`（配置体检，只读）、`memory-lint.mjs`（记忆库体检）、`install.mjs`（把 config/ 装进本机，默认 dry-run，不碰 opencode.json）。

## 给谁用

- 已订阅或打算订阅 OpenCode Go 的个人开发者。
- 中度使用：每天用 opencode 几个小时，配置成本摊得薄。
- 在中国网络环境下工作，想避开"多开 API、多充余额、配代理"这些消耗。
- 想读懂自己配置的每一行，不接受装个插件当黑盒。

只是偶尔问 AI 一句话的人不适合这套：多角色往返会拖慢一次性问答，直接问模型才是对的做法。

## 和 oh-my-opencode 的区别

oh-my-opencode（下称 omo）和本仓库做的是同一件事——给 opencode 一套现成的工作流——形态相反：

| | oh-my-opencode | ocgo-kit |
|---|---|---|
| 形态 | TypeScript 插件 | 纯文本配置（`.md` + JSON 示例） |
| 安装 | 一键安装 | 按作业单装或手动抄 |
| 可见性 | 功能全，实现在编译好的代码里 | 每一行可读、可删、可改 |

两者的分别，是"省心"和"透明"之间的取舍，不是优劣：选哪边，取决于出问题时你想翻插件的文档，还是翻自己装进去的文本。

## 7 个角色

| 角色 | 定位 | 职责 | 边界 |
|---|---|---|---|
| `build` | 主管 | 需求澄清、任务拆分、验收、编排 | 自己不碰文件，改动一律委派 |
| `plan` | 规划 | 只产出规格和计划 | 不写实现代码 |
| `general` | 执行 | 实现、调试、测试、验证 | 唯一能改代码的角色 |
| `explore` | 检索 | 只读找文件、找定义、查资料 | 不写不改 |
| `advisor` | 评审 | 计划评审、过程复核、疑难咨询 | 只判断，不动手 |
| `final` | 仲裁 | 定稿、改过两轮以上、意见冲突时复核 | 低频，不常驻 |
| `writer` | 内容 | 文档、PPT 文案、对外文字 | 不做技术判断、不改代码、不跑命令 |

另有 title / summary / compaction，是 opencode 的隐藏维护代理，会话选择器里看不到它们属于正常现象。

为什么这么分、边界凭什么这么划，写在 [docs/00-为什么这样搭.md](docs/00-为什么这样搭.md)。

## 8 个流程

新项目、功能、计划、验收、收尾、继续、委派、更新知识库，一个流程一个 `.md`，都在 `config/workflows/` 下。

会话开场，主管根据话题判断该走哪个流程，读对应的文件照着走；没装 memory 也有类别兜底路由，用法不变。bug 和小改免流程，直接修。

流程写成文件而不是塞进一个大 prompt，理由有三个：按需读取、不占上下文；想改哪个流程，动那一个文件就够；总纲只留路由，不堆细节。

## 门禁四条

四条硬规则，原始定义只在 `config/AGENTS.md` 一处，其他文件只引用、不复制：

1. 没有可测的验收标准，不进计划；规格、计划没确认，不写代码。
2. 只动计划内的文件；规格/计划要改，先停下来改计划，不擅自扩范围。
3. 停点 = 每个能独立验收的增量。增量结束时：跑验收命令 → 贴输出 → 确认 → 提交。
4. 报任何数字或"已完成"，必须能贴出产生它的最后一次命令输出；贴不出，就标"未验证"。

角色可以换，模型可以换；把门禁四条拿掉，这套配置就退化成一份普通的提示词合集。

## 模型档位

Go 套餐内养起来的档位对应关系：

- 主力（build / plan / general）：DeepSeek
- 评审（advisor）：GLM
- 仲裁（final）：Kimi——特意和 GLM 异构，不一起犯同样的错
- 写作（writer）：Qwen
- 检索（explore）、压缩（compaction）：便宜的 Flash 档
- 标题/摘要（title / summary）：最快的小模型

配置里不锁具体版本号：模型迭代快，这里给的是"档位对应关系"，具体 ID 以你套餐当前可用列表为准。档位怎么分、为什么这么分，见 `docs/02-额度分配.md`（待补）。

## 为什么全用一家

理由很朴素：不用开第二个 API，不用管多份余额，账单只有一张。对国内用户来说这是省事，不是技术选择——多开 API 意味着多份充值、外加配代理，哪家额度用完了还得自己记。

没有 Go 订阅，这套配置照样能用。它是"角色 + 档位"的结构，不绑定任何一家：把每个档位换成你手上的模型即可。不同角色用不同来源的模型，才有交叉验证的效果；用同一家的多个模型也能跑，只是纠错能力会弱一些。

## 怎么开始

两条路：

1. **让 AI 装**：把 `PROMPT.md` 里的提示词整段复制，粘给你正在用的 AI（Claude Code、opencode、Cursor 等都能用），并把本仓库放在它能读到的目录里。它会按作业单来：先检查环境、先列出现有配置、先备份、只增不覆盖、要问的一次问完、合并结果贴给你过目之后才写盘。
2. **手动装**：看 `docs/01-安装.md` 一步步来（待补）。

装完重启 opencode，会话选择器里能选到 7 个角色，就成了。

> 注意：对仓库自带的模板目录跑 `scripts/doctor.mjs` 会出现 1 个 FAIL——模板里故意留着 `<provider>` 占位符，这是正常的；装到你自己的配置目录后再跑，才是真实体检结果。

## 局限

- **比单模型慢。** 多角色往返，拆分、委派、复核都要时间；急的时候，这套结构是负担。
- **不是开箱即用。** 路径、模型 ID、要不要装 memory，都得自己填。
- **没有报错兜底。** 配置是纯文本，改错就直接不生效，opencode 不会提醒哪里错了。
- **是个人实践。** 不是经过团队验证的工程方案，用法不一定适合所有人。

## 维护

本仓库由个人维护，不承诺与 oh-my-opencode 功能对等，也不承诺长期支持。

这套配置会随 opencode 版本和模型迭代继续更新；版本变化导致配置失效时，优先保证 README 和安装文档可执行。欢迎提 issue 报告具体报错，但不保证修复。
